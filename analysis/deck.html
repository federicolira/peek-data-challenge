Appendix · Data modelPeek · Product & BI Analyst Challenge

One fact table and two joins — each checked to add columns, never rows

Join rules applied
  1. Pick the grain first. order_items is one row per line item, so orders and customers are counted with DISTINCT.
  2. Count rows before and after every join. Joining inventory_items: 45,373 before, 45,373 after.
  3. Skip joins that add nothing. order_items already carries the order’s user_id and status (0 mismatches), so orders is never joined.
  4. Aggregate before joining one-to-many. Task D rolls line items up to one row per order before attaching users.
Black = joined in the analysis · grey = available, not needed. Every key checked for orphans: 0 line items without an order, user, product or stock unit. Row counts are whole tables as of the query date.A1

Appendix · AI in this analysisPeek · Product & BI Analyst Challenge

AI wrote the first draft of every query; a check that could fail decided whether to keep it

Where it sped things up
  • Profiling the seven tables and every join key in minutes
  • First drafts of CTE-structured SQL for all four tasks
  • Generating this deck reproducibly from the query outputs
Where checks overruled it
  • A Task D column was 100% or 0% by construction — caught, and the query rebuilt at monthly grain
  • A 100% churn month — identified as the edge of the data, not an event
  • “Retention is near zero” — revised once repeat timing was measured
What I would automate next
  • Run the QA queries on a schedule and alert when a check fails, before a dashboard refreshes
  • Have an LLM draft the weekly KPI narrative with every figure pulled from SQL, never computed by the model
  • Point text-to-SQL at curated, documented views rather than raw tables, so definitions are fixed upstream
Checks that ship with the repo
  • Row counts before and after every join
  • Identity assertion: new + returning = active, every month
  • Revenue reconciled to the status breakdown
  • Definition sensitivity: churn under two definitions
